# 视口驱动设计 —— 全站第一原则

- **状态**：已完成
- **创建日期**：2026-10-01
- **领域**：设计原则（`DESIGN.md` §0.5 / `DECISIONS.md` DEC-020）

## 目标

给页面组织建立一条**成文的判据**，回答「页面上该有什么」——而不是「页面长什么
样」；并把「删除」也纳入授权范围，让「这个段该不该存在」从审美争论变成可判定
的问题。

## 执行结果

**用户提出并定案为全站第一原则**，写入 `DESIGN.md` §0.5，并记入 `DEC-020`。
产出两份文档：

- `DESIGN.md` §0.5（§0.5.1–§0.5.6）
- `PAGE-SPECS/_viewport-audit.md` —— 视口合规审查报告，实测 **123239 字节**
  （约 122 KB），**83 个视口 / 24 条合并建议**，判据来源即 §0.5.1 与 §0.5.2

## 重要结论

1. **一个视口 = 一个核心问题。** 每个主要视口最多：**1 个 Primary Message ｜
   1 个 Primary Visual ｜ 1 个 Primary Action ｜ 0–2 个 Secondary Actions**；
   🔴 禁止同一视口内多个不同业务目标互相竞争。
2. **★ 合并或删除律**：「**如果两个连续 Section 没有回答两个不同的问题，则应
   合并或删除**」。
   - 这是一条**删除授权**，判据是一句话：「**删掉它，读者会缺少什么答案？**」
     答不上来 → 合并或删除。
   - **推论：段数不是越多越好，是「问题数」越多越好。**
3. **视口 vs 段**：视口 = 用户一屏所见（承载一个核心问题）；段 = 页面结构单元。
   **一个视口可以含多个段**，但同一视口内的段**必须共同服务于同一个问题**，
   否则就该拆成两个视口（左右分栏服务同一问题是允许的，不把原则用成教条）。
4. **询盘组件必须完整落在一个视口内**（`DEC-021`，定为硬规则、**不可协商**）：
   用户滚动到询盘表单时，**整个表单（含提交按钮）必须在同一屏内完整可见**。
   - ⚠️ 这条规则**优先于「视口高度尽量饱满」** —— 宁可表单周围留白，也不把
     表单拉长到超出视口。
   - 两条设计约束：① 表单要短（必填 ≤ 3 个）② 表单前后不得放第二个 CTA。
   - 推论：**询盘页视口划分天然由表单尺寸决定** —— 先量表单，再决定它还容得下什么。
5. **这条原则高于 `DESIGN.md` 其余所有内容**，且与视觉无关 —— 它决定的是页面
   上**该有什么**。任何新增段落都要能回答「它回答了哪个前面没回答过的问题」。
6. **⚠️ 诚实记账（必须写下来）**：写文档时我一度把用户举例的六屏示例
   （Who / What / Which wheel / Customize / Trust / Inquiry）写成「**本站认知
   路径实证**」，当成既定事实写进了 `DESIGN.md` §0.5.4。用户明确纠正
   「**不是我们现在需要修改的，我只是提供一个例子**」→ **已撤掉**，改为
   「**格式示例，不是本站既定顺序**」。该更正也已回声到
   `PAGE-SPECS/_viewport-audit.md` 开头的「前提更正」段。
