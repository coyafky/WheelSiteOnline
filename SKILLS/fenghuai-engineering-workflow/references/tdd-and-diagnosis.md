# TDD 与证据化诊断

本参考适配自 Matt Pocock 的 `tdd` 与 `diagnosing-bugs`。

## 1. 测试接缝

测试应从公共接口观察行为，不绑定私有实现。本项目优先接缝：

- 页面与组件：用户可见 DOM、交互、URL、可访问名称和控制台；
- Next API：HTTP 状态、响应契约、幂等和外部服务适配器；
- WordPress：REST 端点、专用表不变式、事务、权限与 outbox；
- 产品发布：公开集合函数、目录/详情/筛选/sitemap 的共同门槛；
- 内容接缝：类型化模块的公共返回形状，而不是组件内部常量。

只有接缝选择会改变公共契约或测试成本时才需要用户确认；已有架构已经指定接缝时直接遵循。

## 2. Red → Green

1. 写一个只描述当前纵向行为的测试。
2. 运行并确认它因目标行为缺失而失败，不是环境错误或拼写错误。
3. 只实现让该测试通过的最小代码。
4. 重跑最窄测试，再跑相关回归。
5. 进入下一条行为前保持绿灯。

禁止：

- 先写一批想象中的测试，再一次性实现；
- mock 私有调用并把调用次数当业务行为；
- 用与实现相同算法重新计算期望值；
- 为未来可能需要的功能预留抽象；
- 没见过红灯就声称测试能捕捉缺陷。

## 3. 缺陷诊断六阶段

### 阶段一：反馈回路

先得到一条已经运行过、能准确捕捉用户症状的命令。优先级：测试 → HTTP 脚本 → CLI
夹具 → Playwright → 请求重放 → 最小 harness → 压力/模糊测试。

反馈回路必须：可变红、可重复、够快、可由 agent 独立运行。输出中的密钥、Cookie、
授权头和个人信息必须脱敏。

### 阶段二：复现与最小化

确认复现的是用户报告的同一个错误，然后逐项删减输入、配置和步骤，直到剩余条件都
不可再删。

### 阶段三：提出假设

列出 3–5 个按可能性排序的假设。每个假设必须写出可证伪预测：如果原因是 X，改变 Y
以后具体信号应如何变化。

### 阶段四：定向探针

一次只改变一个变量。优先调试器或边界日志，不做“把所有东西都打印出来再搜索”。临时
日志统一加唯一前缀，例如 `[DEBUG-a4f2]`。

### 阶段五：修复与回归

在正确公共接缝把最小复现固化成回归测试，先看它失败，再修复，再看它通过。随后重跑
原始、未最小化的场景。

### 阶段六：清理

- 原始复现不再失败；
- 回归测试通过；
- 临时日志和探针已删除或放到明确的验收脚本目录；
- 根因、修法和未覆盖边界已写入任务/决策记录。
