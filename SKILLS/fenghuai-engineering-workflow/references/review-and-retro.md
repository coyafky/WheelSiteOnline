# 双轴评审与工程复盘

本参考适配自 Matt Pocock 的 `code-review` 与 `retro`。

## 1. 双轴评审

先固定比较基点，例如某个 commit、分支、tag 或任务开始前的工作树。没有基点时，明确
说明只能审查当前 diff，不能证明范围完整。

### 规范轴

检查改动是否符合：

- 根及近目录 `AGENTS.md`；
- 当前 Next.js 文档与 TypeScript strict；
- 内容接缝、证据纪律、发布门槛、设计令牌和声明式动效；
- 安全、隐私、最小权限和不可逆动作约束；
- 仓库已有 lint/typecheck/build/测试规则。

工具已经确定能捕捉的问题不重复写成主观建议。仍应注意这些判断型代码气味：神秘命名、
重复逻辑、数据团、原始类型滥用、重复条件分支、散弹式修改、发散变化、投机抽象、过长
调用链和只做代理的中间层。

### 规格轴

逐条对照来源规格、任务和验收条件，检查：

1. 要求是否遗漏或只完成一半；
2. 实现是否表面存在但行为错误；
3. 是否加入未被要求且扩大风险的功能；
4. 页面、API、数据、SEO 与发布门槛是否保持一致。

两个维度分开报告。一个维度通过不能抵消另一个维度失败。

## 2. Finding 格式

按 P0/P1/P2/P3 从高到低，只报告可执行问题：

```text
[P1] 标题
文件与行号：
触发条件：
实际影响：
修复方向：
```

评审默认只读，不自动修改代码。用户明确要求修复时再进入实现流程。

## 3. Session 复盘

复盘关注 agent 的工作环境，不把它写成泛泛心得：

- **导航**：是否难以找到正确文件，是否需要索引或指针；
- **自动检查**：本次错误能否变成测试、lint、CI 或验收脚本；
- **规则质量**：机械规则应自动化，只有判断型规则才写文档；
- **工具经济**：是否存在重复、昂贵或低信号的工具调用；
- **信息访问**：是否缺日志、只读后台、测试账号或第三方状态；
- **无效规则**：是否存在过时、冲突或从不改变行为的说明。

建议按严重度列出，不为“显得完整”而制造改进项。涉及架构或流程正本时按项目路由更新
相应文档。

## 4. 收尾证据

最终报告至少包括：

- 实际修改的文件；
- 实际运行的检查及结果；
- 尚未验证的边界；
- 外部副作用，例如测试邮件、数据库记录、账号或部署变化；
- 是否 commit、push、deploy；
- `STATUS.md`、任务和决定是否已同步。
