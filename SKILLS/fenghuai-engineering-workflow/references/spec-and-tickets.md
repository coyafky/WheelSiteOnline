# 规格与纵向 Issue

本参考适配自 Matt Pocock 的 `to-spec` 与 `to-tickets`。

## 1. 什么时候需要规格

- 页面、API、数据契约、权限或模块边界会改变；
- 多个角色需要共同验收；
- 工作会跨多个 session；
- 存在明确的范围取舍或发布门槛。

对一处明显文案修正、单个样式缺陷或已有规格内的小修，不强制新建完整规格。

## 2. 规格模板

页面规格优先沿用 `PAGE-SPECS/` 的既有模块编号。其他规格至少包含：

```markdown
# 标题

## 问题
从用户或业务角度说明当前不能完成什么。

## 目标结果
说明完成后用户能够做什么。

## 用户故事
1. 作为……，我希望……，从而……

## 实现决定
- 模块边界、公共接口、数据契约和发布门槛。

## 测试决定
- 要测试的公共接缝、正反例和相似先例。

## 非范围
- 本次明确不做什么。

## 待确认
- 仍需要业务、工程、法务或管理层回答的问题。
```

规格描述行为和决定，避免写易过期的具体文件路径或大段代码。只有原型中的状态机、
schema 或类型形状比文字更准确时，才摘录最小片段。

## 3. 纵向 Issue 规则

每个 Issue 都必须满足：

1. 交付一条从输入到可观察结果的窄路径，而不是“先写全部数据库、再写全部 UI”。
2. 能独立演示、测试或复核。
3. 有明确验收标准和阻塞关系。
4. 一个新 session 可以完成。
5. 使用项目领域语言，不另造同义词。

任务文件格式：

```markdown
# <编号或标题>

- **状态**：待开始
- **创建日期**：YYYY-MM-DD
- **来源规格**：<路径或 DEC 编号>

## 要交付的用户行为

## 阻塞于

无，或列出真实阻塞任务。

## 验收标准

- [ ] 条件一
- [ ] 条件二

## 非范围
```

## 4. 大范围迁移

当一次机械改动会同时破坏大量调用方时，采用：

1. **Expand**：新增新接口并保留旧接口，保持全绿。
2. **Migrate**：按可独立验证的批次迁移调用方。
3. **Contract**：全部迁移完成后删除旧接口。

每一步单独建任务并写明阻塞边，不能让仓库在中间状态长期红灯。
