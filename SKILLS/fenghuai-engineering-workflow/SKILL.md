# 丰怀工程工作流

本技能是 `mattpocock/skills` 工程方法在本项目中的中文适配层。核心原则保持一致：
先对齐问题，再以可验证的纵向切片推进；先建立反馈回路，再判断原因；实现与评审
分开；所有结论都要有证据。

## 1. 不可覆盖的项目约束

1. 项目记录一律使用中文。代码标识、协议字段、命令与第三方专名可以保留英文。
2. `AGENTS.md`、更近目录的 `AGENTS.md` 和用户当前要求优先于本技能。
3. 未经明确授权，不得 commit、push、deploy、修改 DNS、真实群发、付费或执行其他
   不可逆/对外动作。
4. Issue 正本仍是 `work/queued/`、`work/active/`、`work/completed/`。除非用户明确
   要求，不另建 GitHub Issue 或 `.scratch/`，避免两套状态漂移。
5. 页面规格进入 `PAGE-SPECS/`；系统形状进入 `ARCHITECTURE.md`；架构决定进入
   `docs/adr/`；流程决定进入 `DECISIONS.md`；当前事实进入 `STATUS.md`。
6. 保持内容接缝、无图不上架、未确认不上架、OpenNext、不发布竞品内容等项目硬约束。
7. Next.js 代码改动前读取当前安装版本的相关文档；定位代码先使用 CodeGraph。

## 2. 先选择工作模式

收到工程请求后，只选择当前需要的最小模式：

| 请求类型 | 使用模式 | 必读参考 |
|---|---|---|
| 需求仍会改变结果 | 需求澄清与规格 | `references/spec-and-tickets.md` |
| 需求明确、需要规划 | 规格与纵向 Issue | `references/spec-and-tickets.md` |
| 新功能或可测试修复 | TDD 纵向切片 | `references/tdd-and-diagnosis.md` |
| 故障、回归、性能问题 | 证据化诊断 | `references/tdd-and-diagnosis.md` |
| 用户要求审查变更 | 规范/规格双轴评审 | `references/review-and-retro.md` |
| 有意义工作结束 | 收尾与复盘 | `references/review-and-retro.md` |

不要因为技能存在就强迫每个小改动生成完整规格。简单、局部、低风险且目标明确的改动，
可以直接建立一个最小验收信号后实施。

## 3. 标准工程链路

### 3.1 对齐

1. 用一句话重述用户要解决的问题。
2. 读取当前任务所需的最少上下文，遵守 `AGENTS.md` 的渐进加载顺序。
3. 区分事实、假设和待确认项。会实质改变结果的歧义才询问用户。
4. 若涉及模块边界，先更新架构；若涉及类型化内容契约，记录流程决定。

### 3.2 规格

1. 从用户视角写问题与结果，不先罗列文件。
2. 明确范围、非范围、接口/接缝、发布门槛和验证方式。
3. 页面工作复用现有 Page SPEC 编号体系；非页面工作写入活动任务文件。
4. 只有难以逆转、没有上下文会令人意外、且真实存在取舍的决定才写 ADR。

### 3.3 Issue 拆分

1. 每个 Issue 是可独立演示或验证的纵向切片，尽量穿过 UI、API、数据和测试。
2. 明确 `Blocked by`，先完成没有阻塞的前沿任务。
3. 一个 Issue 应能在一个新上下文窗口内完成。
4. 大范围机械迁移使用 expand–migrate–contract，不强行伪装成纵向功能。
5. 任务文件从 `queued → active → completed` 移动，不复制多份状态。

### 3.4 实现

1. 先写下要验证的公共接缝和用户可见行为。
2. 能写自动测试时执行 red → green：先看到针对目标行为的失败，再写最小实现。
3. 一次只推进一个纵向切片，不预先实现尚未要求的功能。
4. 频繁运行最窄的相关检查；完成后再运行完整门禁。
5. 调试必须先建立能捕捉用户原始症状的反馈回路，再提出 3–5 个可证伪假设。

### 3.5 评审

评审时分开报告两个维度，不能互相抵消：

- **规范轴**：是否符合仓库规则、当前 Next 文档、内容接缝、安全与可维护性要求。
- **规格轴**：是否完整实现来源规格，是否有遗漏、误实现或范围蔓延。

按严重度先写问题，给出文件与紧凑行号。没有可执行问题时明确写“未发现阻断问题”，
并说明尚未覆盖的测试边界。

### 3.6 完成与复盘

1. 运行与改动风险相称的验证；代码改动至少满足项目完成定义。
2. UI 改动使用 Playwright 验证关键视口、控制台、断图、遮挡和横向溢出。
3. 内容/SEO 改动验证公开集合、robots、canonical、sitemap 与发布门槛一致。
4. 走完 `AGENTS.md` 的 session 收尾清单。
5. 将可机械捕捉的问题优先变成测试、lint、CI 或验收脚本，而不是继续加长规则。
6. 只报告实际运行过的证据；未验证项必须明确降级为 WARN 或未完成。

## 4. 默认完成门禁

按任务相关性选择，但不得用较弱检查代替较强检查：

```bash
npm run lint
npm run typecheck
npm run build
git diff --check
```

询盘/CMS 改动还应运行对应 Docker 验收；UI 改动还应运行 Playwright；依赖或安全相关
改动还应执行依赖审计。若环境缺失，记录具体缺口，不得把“脚本存在”写成“验证通过”。

## 5. 上游与本地适配

上游来源、固定版本和文件校验见 `UPSTREAM.md`；本地偏离及理由见
`.local-patch.md`。更新时先比较上游，再逐条重放本地适配，禁止无审查覆盖。
