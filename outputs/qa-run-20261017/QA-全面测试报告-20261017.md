## 三、缺陷清单

### 🔴 D-01 [P0] 中文 / 西语 / 泰语**首页**全部 404，且语言切换会自动把用户带到这个 404

**影响范围**：`/zh`、`/es`、`/th` 三个首页
**证据**：`shots/01-zh-404.png`

**现象**：
```
curl -o /dev/null -w "%{http_code}" http://127.0.0.1:3000/zh   →  404
curl -o /dev/null -w "%{http_code}" http://127.0.0.1:3000/es   →  404
curl -o /dev/null -w "%{http_code}" http://127.0.0.1:3000/th   →  404
```
页面渲染为「404 / 页面不存在 / 页面可能已移动，或者链接有误。」，`<h1>` 内容即「页面不存在」。

**这不是孤立的死链——它有一条完整的用户触发路径**：
1. 用户在语言下拉选「中文」→ `LanguageSwitcher.pick()` 写入 cookie `fh-locale=zh` 并 `window.location.assign('/zh')`
2. 浏览器发送 `/` + `Cookie: fh-locale=zh` → 服务端 307 重定向到 `/zh`
3. `/zh` 渲染 404

实测：`curl -H "Cookie: fh-locale=zh" /` → `307 → http://127.0.0.1:3000/zh`，跟随重定向后 `<h1>` 为空（404 页）。

**根因（代码层）**：`src/app/page.tsx:34`
```tsx
const result = await getHomepagePageView({ locale, preview });
if (result.status !== "ready") notFound();   // ← 这里抛出 404
```
**根因（内容层）**：WordPress 的已发布页面只有 `home`（slug `home`，ID 1311）与 `home-en`（ID 1461）。**没有** `home-zh` / `home-es` / `home-th` 的已发布页面：
```
$ curl .../wp-json/wp/v2/pages?per_page=100
1461 home-en  publish
1311 home     publish
（无 home-zh / home-es / home-th）
```

**判定**：这是**内容未发布**导致的功能性故障，不是渲染 bug。但用户体验上是硬伤——**海外客户一旦把语言切成中文/西语/泰语，回到首页就看到 404**。

**建议**：
- 短期：为三种语言创建并发布 `home-{locale}` 页面（最小可行：复制英文首页模块结构、填待审文案）
- 或：在 `page.tsx` 里对非英文 locale 的 `status !== ready` 做降级——回落到英文首页并把 `robots` 置为 `noindex`，避免直接抛 404
- 无论哪种，`LanguageSwitcher` 都应在目标语言首页不可用时不下发跳转

### 🟠 D-02 [P1] 6 个已进 sitemap 的页面**完全缺失 robots meta**

**证据**：curl 逐个抓取，`<meta name="robots">` 抓不到

| 页面 | robots meta | 在 sitemap 中 |
|---|---|---|
| `/` | `index, follow` | ✅ |
| `/products` | **缺失** | ✅ |
| `/products/wheels` | `index, follow` | ✅ |
| `/products/ev-components` | `index, follow` | ✅ |
| `/products/custom-aluminum` | `noindex, follow` | ✅（⚠️ 语义矛盾） |
| `/products/safety-tires` | **缺失** | ✅ |
| `/products/wheels/flow-formed` | `index, follow` | ✅ |
| `/capabilities` | **缺失** | ✅ |
| `/custom-development` | **缺失** | ✅ |
| `/about` | **缺失** | ✅ |
| `/dealers` | `index, follow` | ✅ |
| `/dealers/private-label` | `index, follow` | ✅ |
| `/insights` | `index, follow` | ✅ |
| `/tools` | **缺失** | ✅ |
| `/tools/offset-calculator` | **缺失** | ✅ |
| `/support/privacy` | `index, follow` | ⚠️ 预发布环境应为 noindex |

**两个问题叠加**：
1. **缺失**：没有 robots meta ≠ noindex（默认仍是可索引），但**让 SEO 审计无法确认意图**，也无法给这些页面做逐页的索引门槛控制。项目的 `STATUS.md` 明确写着「按页面族落实发布资格」，这 6 个页面实际上脱离了该控制。
2. **逻辑矛盾**：`/products/custom-aluminum` 是 `noindex` 却被收进 sitemap —— sitemap 是「请来抓」的信号，noindex 是「别收录」的信号，两者互相矛盾。这种配置会让搜索引擎优先遵守 noindex，从而产生「在 sitemap 里却永不被收录」的软性错误。

**建议**：
- 统一由页面级 `generateMetadata` 输出 robots。缺失的 6 页补齐（明确 `index` 或 `noindex`）
- sitemap 生成时**过滤掉 `noindex` 页面**
- `/support/privacy` 在预发布环境应 `noindex`

### 🟠 D-03 [P1] 全站触控目标大量小于 WCAG 24px 硬线

**证据**：`shots/m-01-home-top.png`、`shots/m-03-wheels-top.png`

**实测（4 视口一致性复现）**：

| 页面 | 视口 | 触控元素 | <24px | 典型样本 |
|---|---|---|---|---|
| `/` | 390×844 | 55 | **18** | 页脚链接 `Wheels` **46×17** |
| `/about` | 390×844 | 53 | **18** | 同上，每页 8 处 |
| `/products` | 390×844 | 59 | **22** | `提交车型信息` **277×17** |
| `/products/wheels` | 390×844 | 150 | **59** | `BROWSE RECORDED FLOW-FORMED WHEELS` **250×18** |
| `/tools/offset-calculator` | 390×844 | 82 | **43** | 步进按钮 `Increment` **15×17**、清空 `Clear` **20×20** |
| `/request-a-quote` | 390×844 | 58 | **26** | 下拉触发器 `Select a product line…` **235×20** |

**判定依据**：WCAG 2.2 SC 2.5.8（Target Size (Minimum)）要求 **24×24 CSS px** 最小。表格中 17–20px 高度的目标全部不达标。

**影响**：这是 B2B 工业站，访客常在中老年采购、车间环境（戴手套）下用手机浏览。15×17px 的步进按钮和 20px 高的输入框极易误触。

**建议**：
- 页脚/正文里的文字链接可用 `padding` 撑到 24px 高度（不改变视觉字号）
- 表单控件统一 `min-height: 44px`（iOS HIG / Material 建议值，也更符合表单场景）
- 计算器的步进按钮从 15×17 提升到至少 24×24

> 注：`<input class="peer sr-only">` 这类**视觉隐藏但实际可点**的控件（如 1×1 的 `4x100`）是正常实现，**不计入**该缺陷。

### 🟡 D-04 [P2] 移动端询盘表单：产品线下拉展开后与下方卡片重叠 80px，文字互相叠压

**证据**：`shots/m60-quote-popover-real.png`、`shots/m59-quote-select.png`

**实测（390×844，`vw=390`）**：
```
弹出层 .astryx-popover : top=174, bottom=308   (h=134, w=285)
下方卡片 .bg-soft      : top=228, bottom=354
重叠区域                = 80 px
```

**视觉表现**：截图里可以清楚看到「Wheels」「EV Aluminum Housings」「Custom Aluminum Development」「Self-Sealing Tires」四个选项与「USEFUL DETAILS, IF AVAILABLE」卡片的「· What you need / · What information you already have / · Approximate quantity and market」**文字互相穿透**，两者都读不清。

**根因**：弹出层 `.astryx-popover` 的 `position: relative` 且 **`z-index: auto`**，未建立独立浮层层级；下方卡片 `position: static` 同样 `z-auto`，纯靠 DOM 顺序决定绘制顺序。弹出层没有白色的实底遮挡住全部区域（选项行背景仅 `rgba(0,0,0,0.05)`），导致下层文字透上来。

**判定**：这是第三方设计系统 `@astryxdesign/core` 的 Popover 在移动端窄容器下的层级缺陷，非本项目自研代码。

**建议**：
- 给弹出层容器补 `z-index`（如 `z-50`）建立浮层层级
- 选项行使用**不透明**背景（`bg-white` 而非 `rgba(0,0,0,0.05)`）
- 或改用移动端原生的 `<select>`（iOS/Android 会弹系统选择器，天然无此问题）

```
显示尺寸        : 233 × 233 px
放大倍数        : 233 / 170 = 1.36×
```

最差的 6 张：`12`、`A015`、`A091F`、`AV08`、`CG02B`、`CG02P` —— **全部是 171×171 原图撑到 233×233**。

**WordPress 侧佐证**：
```
18-ff107.webp | orig: 150 x 136 | sizes: {}   ← 原始文件就只有 150×136，无任何缩略图尺寸
```

**判定**：**内容资产问题，不是代码问题**。前端已经在用 Next.js Image 优化管线（`/_next/image?url=...`），但源头分辨率不够，优化无从发挥。

**影响**：轮毂是产品官网最核心的视觉资产，客户靠图片判断工艺与款式。1.36 倍放大在 Retina 屏上（DPR 2）实际是**放大 2.7 倍**，肉眼可见模糊。

**建议**：请设计/供应商补 **≥800×800** 的原始产品图重新上传。上传后 Next.js 会自动生成多档尺寸，无需改代码。

### 🔵 D-07 [P3] 图片 alt 缺失与 title 品牌名重复

**证据**：DOM 扫描

**alt 缺失**：`/products` 有 4 张图 `<img>` 的 `alt` 属性缺失或为空，`/products/wheels` 有 1 张。均为装饰性产品线缩略图。装饰图理论上应写 `alt=""`（无障碍正确做法），但缺失 `alt` 属性本身会让屏幕阅读器读出文件名，仍属缺陷。

**title 重复品牌**：
```
/products → "Automotive Product Lines | Fenghuai | Fenghuai"
```
`Fenghuai` 出现两次。其余页面（如 `/products/wheels` → `"Wheel Catalogue | Sizes, PCDs & Production Specifications | Fenghuai"`）正常，说明是 `/products` 页面的 title 字符串自带了品牌名，又叠加了模板的 `| Fenghuai`。

## 五、关于“进场动画褪色”的复核结论

测试过程中在 `/tools/offset-calculator` 曾截到整块内容**半透明褪色**的画面（`17-offset-form-result.png`）。经查证：

- 该区块的 `<section>` 有 `transition: opacity, transform, filter`，滚动进入视口时会播放 fade + blur 动画
- 截图瞬间恰好卡在动画中间帧
- 等待 3 秒后重新截图（`18-offset-stable.png`），区块完全恢复正常，`opacity: 1`、`filter: blur(0px)`

**结论：这是滚动进场动画的正常表现，不是缺陷。** 但需提示一点——若用户快速滚动并截图/打印，可能得到中间态；若要规避，可加 `@media (prefers-reduced-motion: reduce)` 直接跳过动画。

## 六、测试方法的已知局限（诚实声明）

1. **视口覆盖方式的局限**：用 CDP `Emulation.setDeviceMetricsOverride` 模拟，**不是真机**。iOS Safari 的地址栏收放、软键盘弹出对布局的挤压、Android 返回键行为等均未覆盖。
2. **中途出现过的误判已纠正**：测试中曾因 CDP 视口覆盖被重置（`vw=1600` 却以为是 390），一度把下拉弹层判为「宽 695px 溢出视口」，实际在真实 390px 下是 285px、不溢出。相关误报已剔除，**未写入缺陷清单**。
3. **未测项**：
   - 询盘表单**最终提交**（会触发真实 QQ SMTP 发信，按要求只测到提交前的校验）
   - 软键盘遮挡、真机触控精度
   - 键盘 Tab 焦点顺序、屏幕阅读器朗读（仅做了 DOM 属性层面的 alt / aria 检查）
   - `/zh`、`/es`、`/th` 三种语言的**内容质量**（页面能开，但译文审校状态未评估）
4. **未改动任何项目源码**，未重启 dev server，未写入 WordPress。
5. 视觉截图受 `captureScreenshot` 一帧延迟影响，个别帧经“连拍两次”规避；正文引用的截图均已目视确认。
