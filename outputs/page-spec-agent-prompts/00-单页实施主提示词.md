# 单页实施主提示词

把下面整段复制给执行页面开发的 agent，并替换尖括号中的内容。

```text
你正在 `/Users/fkycoya/Documents/Code/WordpressWheelSIte` 中实施一个真实页面，不是在写方案。

目标路由：<例如 /products/ev-components>
唯一施工规格：<例如 PAGE-SPECS/ev-components.md>
本次任务名称：<例如 新能源三电铝制品页面实现>
本次额外约束：<没有则写“无”>

请从现有仓库状态继续工作，完整实现、验证并收尾，不要只输出计划，也不要在可以依据 Page SPEC 和仓库现状自行判断时停下来提问。不要 commit、不要 push、不要发布上线、不要真实发信、不要花钱或修改 DNS。

一、先按仓库契约加载上下文

1. 完整阅读根目录 `AGENTS.md`。
2. 按 AGENTS 的渐进式顺序读取：`PROJECT.md`、`STATUS.md`、`ARCHITECTURE.md`、目标 Page SPEC、相关 `DECISIONS.md` 条目、目标路由现有代码。
3. 如果仓库根存在 `.codegraph/`，理解或定位代码时先用 `codegraph explore`；不存在才使用 `rg`。
4. 写 Next.js 代码前，读取 `node_modules/next/dist/docs/` 中与本次路由、Server Component、Image、数据获取相关的当前版本文档。不要依赖记忆中的旧版 Next.js API。
5. 只读取本任务需要的文件，不要一开始扫描全仓库。

二、先建立任务记录，再改代码

在 `work/active/` 新建 `<日期>-<页面>-implementation.md`，写明：

- 路由和 Page SPEC；
- 本次要替换的旧内容；
- 计划接入的 WordPress 媒体 ID；
- 内容与证据边界；
- lint、typecheck、build、四视口、WordPress live、fallback、no-JS 和 standalone 验收项。

三、审计现状与证据

1. 对照 Page SPEC 列出每个视口编号及其回答的客户问题。
2. 检查现有路由、内容文件、组件和数据来源，找出：
   - 虚构型号、规格、产能、认证、案例、合作品牌或承诺；
   - 竞品文案、品牌、图片路径或专有标题；
   - 无报告支持的数字和把供应商能力写成深圳法人自有能力的内容；
   - 会破坏 Page SPEC 顺序或移动端体验的旧组件。
3. 现有 WordPress 图片可以读取，但“图片可用”不等于“图片证明某项主张”。图片只证明可见环境；型号、测试、认证、产能和法人范围仍需独立证据。
4. 找到不确定数据时，诚实省略或保留 Page SPEC 规定的限定状态。不要为了页面完整而补猜测值，也不要用系列通用规格替代实际 variant。

四、保持内容接缝

1. 在 `src/content/types.ts` 定义或复用稳定视图模型；组件不得直接读取 WordPress 原始 JSON。
2. 页面文案、CTA、边界说明、媒体对象和输入清单放入 `src/content/<page>.ts`，不要硬编码进 React 组件。
3. 类型变更等于 WordPress 内容契约变更，必须在 `DECISIONS.md` 新增一条决策记录，写清原因和影响。
4. 媒体统一使用 `MediaAsset`：`wordpressId`、本地 `src`、`alt`、`caption`、`hasRender`、`approvalStatus`、`sourceRef`。
5. 保留 `hasRender` 与批准状态兜底。WordPress 不可用时必须回退到同一张批准图片的本地 WebP，不能产生空框或 404。
6. 如果一个页面有多张媒体，使用 `resolveWordpressMediaCollection` 一次批量解析，禁止逐张串行请求。

五、实现页面

1. 按 Page SPEC 的视口顺序实施。一个视口只回答一个核心问题，并让标题、主视觉、边界说明和 CTA 服务同一个问题。
2. 页面路由保持 Server Component；WordPress fetch 放在 `src/lib/wordpress/<page>.ts`。
3. 页面组件放入 `src/components/<page>/`，只消费类型化内容 props。
4. 使用 `src/app/globals.css` 中的设计令牌和现有按钮/容器原语；组件内不写裸 hex。
5. 动效只用 `data-reveal`、`data-reveal-group`、`data-parallax-media`，不要手写 IntersectionObserver。无 JavaScript 时内容必须可见。
6. 使用 `next/image`，为动态 WordPress 图片提供正确的 `sizes`；低分辨率竖图不强制裁成桌面通栏。
7. CTA 必须携带 Page SPEC 要求的 `product_line`、`intent`、`customer_type`、`model` 或 `productionCode` 上下文。
8. 不把竞品的业务分类、文案、素材和品牌残留到产物中。只借鉴允许的结构和交互节奏。
9. 没有核准型号数据的产品线只做能力页，不创建假 SKU、假价格、假库存或假车型适配。

六、WordPress 媒体

1. 按 Page SPEC 的媒体 ID 批量读取实际像素、标题、alt、caption 和 URL，确认图片内容确实对应指定视口。
2. 为每张公开图片生成或确认同图 WebP 回退，文件名使用清晰的英文语义名。
3. 在本地 WordPress 中补齐：alt、caption、`fh_source_entity`、`fh_source_document`、`fh_source_page`、`fh_usage_scope`、`fh_content_role`、`fh_brand_visibility`、`fh_claim_ids`、批准人与日期。
4. 测试图片关联 `fh_test_record_id`；研发/生产图片关联负责主体。不要从文件名推断工艺、型号或测试结论。
5. 不修改或隐藏来源品牌标识来制造“自有图片”印象；是否公开按用户已经确认的媒体库可用范围和 Page SPEC 选择执行。

七、分层验证

代码阶段：

- 先跑 `npm run typecheck` 和 `npm run lint`；
- 搜索本页禁止词、旧性能数字、`PLACEHOLDER` 和竞品残留；
- 修完后跑 `npm run check`。

浏览器阶段：

- 用真实浏览器滚动整页，触发声明式 reveal 和图片懒加载后再截图；
- 验收 1440×900、1280×800、390×844、360×800；
- 每个视口检查图片加载失败数与 `document.documentElement.scrollWidth === clientWidth`；
- 检查一个 H1、Page SPEC 规定的 H2 顺序、CTA 查询参数、键盘可达链接；
- 建立禁用 JavaScript 的浏览器上下文，确认正文、六/全部主标题和 CTA 仍然可见；
- 用移动宽度作为 200% 放大的等效检查，关键内容不能依赖横向滚动；
- 截图保存到 `outputs/<page>-review/`。

生产阶段：

- 运行 `npm run check`；
- 启动 `.next/standalone/server.js` 做真实路由 200 冒烟；
- WordPress live 模式核对页面使用的媒体 URL 数量；
- WordPress mock 或不可用模式核对所有图片切到本地 WebP，且页面仍 200；
- 对渲染后的正文扫描禁止词，避免 CSS 类名造成假阳性。

八、完成收尾

1. 把 Page SPEC 状态改为“已实现”，只勾选有实际证据的验收项。
2. 更新 `STATUS.md`：当前完成、仍未完成、下一步和阻断项。
3. 如果改了类型、发布集合、证据口径、数据流或页面边界，更新 `DECISIONS.md`；架构改变时同步 `ARCHITECTURE.md`。
4. 更新 `outputs/README.md`，登记视觉交付物。
5. 在任务文件写入真实验收数据，再从 `work/active/` 移到 `work/completed/`。
6. 跑 `git diff --check`，报告修改但不要 commit 或 push。

最终回复必须用中文，先给结果，再列：实现的 Page SPEC 视口、内容/证据边界、WordPress 媒体数量、验证结果、关键文件和截图目录。不要把“构建通过”写成“已经部署上线”。
```
