# 项目增量路线图：第一性原理与纵向切片计划

日期：2026-10-10
适用范围：Next.js 前台、Headless WordPress、询盘、邮件、内容运营与正式上线准备。

## 一、第一性原理：这个项目真正交付什么

先把所有页面、筛选、动画和后台字段还原成最小业务链路：

```text
客户找到可信的已批准产品
  → 能带着准确规格提交需求
  → 询盘可靠落库且不重复
  → 销售收到可回复的通知
  → 运营无需改代码即可更新产品和文章
  → 历史记录、公开内容和发布状态可追溯
```

因此，增量不是“继续增加页面数量”，而是每次只改善这条链路中的一个可观察结果。
一个增量必须同时回答四个问题：

1. 改善了哪一个用户或运营结果？
2. 哪一个稳定接缝承载它（页面、API、WordPress、outbox 或部署）？
3. 用什么失败测试证明旧问题确实被捕捉并修复？
4. 哪个发布门槛仍然可能阻止上线？

## 二、当前基线与约束

### 已经成立的事实

- 远程 `7080` 是 Headless WordPress，`9080` 是 Next.js Node 运行时；询盘可写入 WordPress，后台可查看。
- 轮毂公开集合、详情、筛选、sitemap 和询盘服务端复核共用稳定契约。
- Insights 首批 6 篇已由 WordPress 自定义 `fh_guide` 接管，前端保留本地回退。
- 询盘已有两步表单、Zod、幂等、限流、outbox、SMTP/Resend 通道与真实合成验收。
- 当前询盘仍是一条轮毂上下文，尚不支持一次提交多款轮毂。

### 不能被增量破坏的约束

- 无图不上架、未确认不上架；WordPress 权威空集合不能回退旧产品。
- 页面只消费稳定视图模型，不直接读取 WordPress 原始响应。
- 询盘先落库再发信；邮件 `accepted` 不等于 `delivered`。
- 不把中文未完成正文伪装成可索引中文页。
- 2 GB 服务器不执行 Next.js 构建；构建在本机完成，服务器只加载经过验证的镜像。
- 不引入支付、订单、客户账号或自研 CRM 来解决询盘问题。

## 三、增量排序原则

按以下顺序排序，而不是按“最容易看见的 UI”排序：

1. **先保护已产生的销售线索**：可靠落库、幂等、投递状态、退信和恢复。
2. **再减少运营改代码成本**：内容和产品字段由 WordPress 正本管理。
3. **再提高公开信息可信度**：首发产品、图片、规格、主体和法律文本全部可追溯。
4. **再扩大转化能力**：多款轮毂询价清单、表单体验、移动端和无障碍。
5. **最后放开索引和正式流量**：域名、TLS、SEO、监控、恢复、UAT 和上线授权。

这个顺序的理由是：一个漂亮但不能可靠接收的询盘页没有商业价值；一个可编辑但发布门槛不清晰的 CMS 会把错误扩大到全站；只有前两层稳定后，UI 和 SEO 的投入才不会返工。

## 四、建议的六个增量阶段

### 阶段 0：基线冻结与外部阻塞分离

**目标**：把可自主完成的工程任务与必须请示的上线条件分开，避免反复返工。

**工程动作**：

- 每个 Issue 只保留一个纵向用户结果，沿 `queued → active → completed` 流转；
- 为正式主体、域名/TLS、发件域名、法律文本、首发产品和 OpenNext 平台建立阻塞清单；
- 保持当前 IP+HTTP、`noindex` 联调环境，不把联调地址当生产环境。

**门槛**：所有“待确认”项有负责人、输入和截止时间；没有把外部阻塞伪装成代码完成。

**可立即开始**：无需上级决定。

### 阶段 1：询盘可靠性生产化

**用户结果**：销售知道每条询盘是否已保存、已接受、已送达或退信；邮件服务故障不会丢线索。

**纵向切片**：

1. COM-020：实现邮件服务商签名事件回调，把 `delivered/bounced/unknown` 写回 WordPress；
2. COM-021：把 outbox worker 接到可靠平台调度，验证租约、退避、5 次放弃和积压告警；
3. 增加一条端到端合成链路：提交 → CPT → outbox → 模拟事件 → 后台状态/通知一致。

**阻塞于**：正式发件域名、邮件服务商账号和回调地址由管理层/运维提供；代码和本地模拟可先做。

**完成门槛**：不再把 `accepted` 展示成最终送达；回调伪造、重复回调和过期签名均有失败测试。

### 阶段 2：多款轮毂询价清单

**用户结果**：客户可以一次选择多款已批准轮毂，并在一封通知中按产品分别说明数量和规格。

**切片顺序**：

1. 扩展 Zod/类型为 `items[]`，最多 20 项；旧单产品载荷保持兼容；
2. 目录/详情添加、删除、改数量、清空和刷新恢复；
3. 服务端逐项按 `model + productionCode` 重查公开集合，拒绝客户端伪造规格；
4. WordPress 保存不可变清单快照，后台展示逐项记录；
5. HTML/纯文本邮件显示同一清单，幂等键仍针对整次提交；
6. 补一款、多款、重复、撤回、篡改、数量越界、重放和邮件失败 E2E。

**阻塞于**：无外部资源，可直接开发；现有 Issue 为 `work/queued/2026-10-09-inquiry-cart-multi-item.md`。

**完成门槛**：旧单产品记录不迁移也能继续读取；产品日后修改不改变历史询盘。

### 阶段 3：WordPress 内容接管扩展

**用户结果**：运营可以在后台改首页、公司、能力页和产品线文案/SEO/媒体，不需要开发部署。

**切片顺序**：

1. 首页与公司级 SEO；
2. 四条产品线能力页；
3. 询盘入口文案与隐私版本；
4. 发布、撤回、预览、缓存失效和 sitemap 一致性；
5. 每个切片完成后再迁移下一组，不做一次性全站重写。

**实现纪律**：采用 expand–migrate–contract；WordPress 响应先适配为现有 `src/content/types.ts`，组件不改成依赖原始 REST 字段；字段不完整时 fail-closed，保留最后一次有效快照。

**阻塞于**：内容审批人和正式文案；工程实现本身可继续。

### 阶段 4：产品与图片可信度

**用户结果**：目录里的每个首发型号都有真实主图、核验变体、供货/图权状态和可追溯来源。

**切片顺序**：

1. 把 138 个技术批准型号收窄成业务、工程、供应、图权共同签字的 10–20 个首发集合；
2. 执行轮毂图片规范化：只裁切、清理背景、归一曝光与压缩，不生成或改写产品事实；
3. 每次变更重新验证目录、详情、筛选、相关推荐、询盘快照和 sitemap；
4. 不合格源图进入补图清单，不用生成图冒充真实 SKU。

**阻塞于**：首发产品签字、图片授权、供应确认；开发可先完成处理流水线和证据模板。

### 阶段 5：中文 i18n 与转化体验

**用户结果**：中文用户看到完整、经过审核的中文页面，而不是只翻译导航的英文页面。

**切片顺序**：

1. 先确定 locale 内容模型和共享字段；
2. 首页、产品总览、四条产品线、询盘页逐页翻译与业务/工程审核；
3. 再做 Insights、工具和政策；
4. 每页完成后才开放 canonical、`hreflang` 和中文 sitemap；
5. 真机软键盘、屏幕阅读器、键盘和 200% 缩放完成 UAT。

**阻塞于**：中文业务/法律内容审核；未完成页继续 `noindex,follow`。

### 阶段 6：正式部署与上线演练

**用户结果**：正式域名上的公开页面、询盘、邮件、后台、备份和回滚均有人负责且可演练。

**前置资源**：正式域名/TLS、OpenNext 平台和区域、WordPress/MySQL 生产实例、邮件 DNS、监控告警预算、备份存储、第二人恢复责任人。

**验收顺序**：

1. 隔离预发布环境部署，与生产配置分离；
2. 核对 `NEXT_PUBLIC_APP_URL`、canonical、OG、robots、sitemap、图片和缓存；
3. 演练数据库/媒体/应用恢复和上一版本回滚；
4. 进行预发布桌面、移动、无障碍和真实邮件 UAT；
5. 业务、销售、工程、法务和技术联合签字后，才申请 DNS、开放索引和正式发信。

## 五、并行泳道与依赖关系

```text
邮件事件/worker ───────┐
                       ├─→ 预发布故障演练 ─→ 上线授权
多款询价清单 ──────────┘

内容适配器 ─→ 首发产品/图片签字 ─→ 中文逐页内容
                                     └─→ 中文 SEO 放行

依赖审计 ───────────────→ 生产镜像门禁
UI 视觉收口 ────────────→ 只能作为上述主线的低风险并行项
```

## 六、每个增量的统一执行模板

1. **对齐**：写一句用户结果，列事实、假设和待确认项。
2. **规格**：写范围、非范围、稳定接缝、发布门槛和阻塞关系。
3. **Red**：先写能捕捉旧问题的公共接缝测试，并确认它因目标行为缺失而失败。
4. **Green**：只实现当前切片所需的最小代码，保持旧路径兼容。
5. **验证**：按风险运行单测、API/CMS、Playwright、构建和安全检查。
6. **双轴评审**：分别检查仓库规范和来源规格，不让一个轴的通过抵消另一个轴的遗漏。
7. **收尾**：更新 `STATUS.md`、必要的 `DECISIONS.md`、任务状态和 `outputs/` 证据；未经明确授权不自动 commit、push 或 deploy。

## 七、下一步建议

### 下一次开发会话优先做

1. 先完成阶段 1 的邮件事件回调和 worker 平台适配的本地可验证部分；
2. 紧接着执行阶段 2 的多款轮毂询价清单；
3. 并行处理开发依赖高危公告核验和当前轮毂目录视觉任务的收尾，不让它们阻塞询盘可靠性。

### 需要向上级一次性请示

- 正式主体、域名、TLS 和 DNS 负责人；
- 正式发件域名、销售收件组、邮件服务商账号和回调权限；
- 首发 10–20 个轮毂型号、规格、供货和图片授权签字人；
- 五份法律文本、中文正文审核人和生效版本；
- OpenNext/生产 WordPress 平台、区域、预算、监控、备份和第二人恢复责任人；
- 预发布 UAT 时间窗与上线/回滚授权人。

以上事项不应混在普通开发 Issue 中；它们是上线门禁输入，不是“再写一点代码”即可解决的问题。
